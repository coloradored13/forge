# Section: Requirements & the MVP line

Enforce quality against INVEST (Independent, Negotiable, Valuable, Estimable, Small, Testable):
- ATOMIC: one requirement = one testable assertion. If a statement bundles capabilities ("search AND download AND export"), SPLIT it into separate requirements. Flag conjunctions and multiple verbs.
- TESTABLE: every requirement needs a done-definition you can stand in front of the built system and answer yes/no. Reject vague quantifiers (fast, quickly, meaningfully, seamless, intuitive) — push to an observable condition or a number.
- NECESSARY (INVEST-Valuable): challenge each requirement's right to exist — "based on your stated problem and goal, do you actually need this?" A requirement that doesn't serve the stated value gets challenged, and if undefendable, flagged.
- NO RATIONALE in the statement (no "so that", "because") — rationale lives in the problem section.
- TYPE each: functional | non-functional | constraint. This is not a label, it ROUTES THE WORK: a functional requirement becomes a user story with scenarios that demonstrate it; a non-functional one or a constraint becomes a tech ticket, verified by measurement or inspection. Getting it wrong sends real work to a stage that cannot verify it.
- FUNCTIONAL means a user does something. Write it from their side — what a person can do and what they get — never as a component or a system property. If you cannot name who benefits, it is probably not functional.
- NON-FUNCTIONAL means how the system must BE: performance, security, entitlement, accessibility, reliability, infrastructure. These are first-class and equal to functional, but they need QUANTIFIED, TESTABLE criteria — "responds within two seconds at fifty concurrent users", never "is fast". An unmeasurable NFR is a wish.
- BEFORE typing something non-functional, TRY INVERTING IT into something a person can or cannot do. "No operation exists that alters or deletes a submitted record" is undemonstrable as written; "a dock lead cannot edit or delete a submitted exception" is an ordinary thing to check. The inverted form is usually the real requirement, and it is verifiable. Only when a requirement genuinely survives that inversion — a guarantee about the system rather than about anyone's experience of it — is it non-functional.
- OWNABLE: every acceptance criterion must be provable by ONE piece of work, and gets its own id (AC-1, AC-2) so downstream work can point at it without reproducing its wording. A criterion quantified over things nobody builds in one place — "through any interface", "on every screen", "in all logs" — cannot be demonstrated by any single unit of work. It can only be disproved by a counterexample, and in practice two people each build half of it and each assumes the other covered the seam. Ask: "where is the ONE place that makes this true?" If there is an answer, phrase the criterion against that place. If there genuinely is no such place, it is not an acceptance criterion; it is a policy, and writing it as a criterion puts a hole in the plan that looks like coverage.
- CONTEXT IS NOT A HIDING PLACE. The context field carries system-specific detail so the statement can stay timeless. It is not drift-checked, nothing tests it, and no acceptance criterion covers it — so behaviour described only in context gets built by whoever reads it, to whatever standard they invent. If context says what the system DOES rather than what it is built on, that is a requirement wearing a disguise: pull it out, give it its own statement, type and criteria.
- THE SHAPE'S WORDS. Every noun in a statement is a term the shape defined, or the statement is drift. Every state a requirement mentions is a state a lifecycle names. A requirement about an `unowned` part of the shape is premature — flag it and hold it past the line.
- Deferred/cut requirements keep their IDs and stay in the object. Preserve existing requirement IDs (REQ-n) if present in prior captures; only mint new IDs for genuinely new requirements.

THE EXPERIENCE PASS (run it once the set stabilizes). Requirements whose experience ships on a delivery surface make LIVED claims, and unquantified lived claims are the gap that let a wireframe pass every gate: for each surface-carried requirement ask what a person standing there could measure — time from first touch to done, targets a gloved thumb hits, one column at handheld width, status visible in daylight — and capture them as acceptance criteria with numbers. State only what evidence can show: "recorded at the dock door" is geography no software evidence can discharge; "requires nothing beyond the handheld" is the same intent, testable.

BIND THE SURFACES: the surfaces were drafted in Solution & Scope without requirement ids. Now that REQ-n exist, re-state each surface with the requirements whose experience it carries, and each deferral with what it consciously leaves without a surface. A committed requirement with lived-experience criteria that no surface carries and no deferral names will be found by the gates — decide it here instead.

DRAW THE LINE (last, required before this section is complete). With the shape known and the requirements stable, the PM draws the MVP line: one sentence a reviewer can quote — what this cycle ships and what it does not — then every committed requirement placed inside it, and everything past it (a requirement, a surface, a lifecycle from the shape) named with the reason it can wait. Twenty requirements for a bakery run sheet is what happens when nobody draws this. Challenge a line that includes everything ("then it is not a line") and a line that excludes the crux ("then what are we shipping?"). The line is the PM's; your job is that it exists, that it is quotable, and that nothing committed is on neither side of it.
