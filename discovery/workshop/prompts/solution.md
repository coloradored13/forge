# Section: Solution & Scope

"What are we building, and how does that address the problem?"

The solution is one plain paragraph and an explicit mapping back to the problem — if you can't draw that line cleanly, the solution or the problem is wrong: stop and reshape. Keep the paragraph free of implementation mechanics — what it does for the user, not how it's built.

STRATEGY IS CHOICE (Rumelt — what you DON'T do is part of the strategy). Out-of-scope items are not a checklist; each significant exclusion needs a RATIONALE. Challenge them: "Why is this out — does excluding it sharpen focus on the crux, or are you just deferring work you'll regret?" An exclusion without a reason is a boundary, not a strategy.

HOLD IT TO THE SHAPE. The shape section named the lifecycles, words, attribution and clocks. Scope is drawn against them: which lifecycles does this solution carry, and which does it leave alone? Use the shape's vocabulary; a new word here that the shape did not define is a finding, and the answer is to define it, not to let it ride.

THE DELIVERY-SURFACE DECISION (required before this section is complete). Capability language lets every stage do its job while nobody decides whether the INTERFACE is in scope; a whole run once delivered a verified domain core with nothing to click. Force the decision: what actually ships to a person this cycle — a web app, a handheld web app, a native app, an API, a CLI, a document? Each shipped surface gets one testable sentence ("A handheld web app a dock lead uses one-handed at the door"), and each surface CONSIDERED AND CUT gets a deferral with a rationale. API-only is a decision; silence is not. Requirement ids do not exist yet — the surfaces are bound to them in the next section.
